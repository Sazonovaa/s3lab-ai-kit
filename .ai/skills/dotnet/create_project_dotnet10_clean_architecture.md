# Назначение
Создать **новый сервис** внутри существующего **.NET 10 / SLNX** решения по канонам **Clean Architecture** с отдельными слоями **Api**, **Application**, **Domain**, **Infrastructure** и **Tests**.

# Роль skill-contract
Этот файл — **skill-contract** для subagent route:

```text
.ai/subagents/dotnet/clean_architecture_service_builder.md
```

Полноценное создание нового сервиса — задача для **subagent**, потому что она создаёт несколько проектов и требует изолированного контекста исполнения. Этот skill-contract задаёт правила, структуру, команды, ограничения и quality gates, по которым subagent обязан работать.

# Когда применять
- Читать как обязательный contract из subagent `.ai/subagents/dotnet/clean_architecture_service_builder.md`.
- Пользователь просит добавить новый backend-сервис в существующий `.slnx` и явно указывает Clean Architecture, DDD, CQRS, MediatR, bounded context, enterprise, сложный домен или масштаб на несколько команд.
- Нужен каркас сервиса с Clean Architecture, CQRS, Result, MediatR, Serilog, HealthCheck и FluentValidation.
- Нужно создать слои сервиса и подключить их в solution без бизнес-логики в контроллерах.

# Когда не применять
- Если пользователь просто просит «создать сервис» без архитектурных сигналов — вернуть управление senior-subagent для делегирования в `.ai/subagents/dotnet/dotnet_project_clarifier.md`.
- Если пользователь просит CRUD, Minimal API, Worker Service, webhook, уведомления, прототип, небольшой или быстрый сервис — вернуть управление senior-subagent для делегирования в `.ai/subagents/dotnet/simple_service_builder.md`, если нет конфликтующих Clean Architecture сигналов.
- Если одновременно есть сигналы простого сервиса и Clean Architecture — вернуть управление senior-subagent для уточнения через `.ai/subagents/dotnet/dotnet_project_clarifier.md`.

# Preflight blockers
Если в запросе пользователя нет названия сервиса:

1. Сразу спросить:

   ```text
   Как назвать сервис? Название укажите латиницей, без префикса Tiss, без названия проекта и без имени слоя.
   ```

2. Сразу остановиться после вопроса.
3. Не искать `.slnx`, не выполнять shell-команды, не строить план создания и не создавать файлы до ответа пользователя.

# Несколько сервисов
Если пользователь просит создать несколько сервисов:

- не создавать несколько сервисов в одном запуске subagent;
- senior-subagent должен запустить отдельный subagent `.ai/subagents/dotnet/clean_architecture_service_builder.md` для каждого сервиса параллельно одним батчем;
- количество запусков subagent должно быть равно количеству уникальных названий сервисов, явно указанных пользователем;
- каждый запуск subagent получает ровно одно название сервиса;
- если названия сервисов не указаны, сразу спросить список названий сервисов и остановиться;
- не искать `.slnx`, не выполнять shell-команды и не строить план создания до получения списка названий.

# Проверка названий сервисов
Правило применяется и для одного сервиса, и для нескольких сервисов:

- после получения названия или списка названий нормализовать каждое название по правилам PascalCase;
- проверить, что нормализованные названия уникальны между собой;
- проверить, что каждое нормализованное название уникально в контексте всего solution и не занято существующим сервисом/папкой/solution folder;
- если пользователь ввёл одинаковые названия или после нормализации появились дубли — остановиться и сообщить пользователю, что названия повторяются и нужно выбрать другие названия сервисов;
- если название уже занято в solution — остановиться и сообщить пользователю, что сервис с таким названием уже существует и нужно выбрать другое название;
- при любом конфликте названий не запускать subagents, не создавать проекты и не менять файлы до ответа пользователя.

# Этапы исполнения subagent
Subagent `.ai/subagents/dotnet/clean_architecture_service_builder.md` выполняет работу по этим этапам. Этот skill-contract не заменяет subagent, а задаёт для него обязательные правила.

1. **Solution Inspector** — read-only этап:
   - найти активный `.slnx`;
   - определить `<НазваниеПроекта>` из имени solution или подготовить вопрос пользователю;
   - проверить доступность .NET SDK 10.x;
   - посмотреть существующие сервисы, чтобы не нарушить локальные соглашения.

2. **Scaffold Builder** — этап создания проектов:
   - создать проекты `Api`, `Application`, `Domain`, `Infrastructure`, `Tests`;
   - добавить проекты в `.slnx`;
   - использовать `--solution-folder <НазваниеСервиса>`;
   - настроить project references между слоями.

3. **Architecture Composer** — этап базовой архитектуры:
   - создать минимальные папки Clean Architecture;
   - подключить CQRS, Result, MediatR, FluentValidation;
   - подключить Serilog, HealthCheck и DI-регистрации слоёв;
   - создать endpoint'ы по CRUD-набору для основной сущности/ресурса, если он указан пользователем;
   - если основная сущность/ресурс не указаны, спросить название сущности/ресурса и не выдумывать его;
   - не добавлять бизнес-фичи сверх CRUD и тестовые сценарии без отдельной команды.

4. **Build Validator** — этап проверки:
   - выполнить `dotnet build <SolutionFile>.slnx`;
   - исправить очевидные ошибки компиляции, возникшие из-за каркаса;
   - если ошибка требует продуктового/архитектурного решения, остановиться и спросить пользователя.

# Входные данные
1. **Solution**: найти активный файл **`.slnx`**. Если файлов несколько — спросить, какой использовать.
2. **Название проекта**: взять из имени solution по формату **`Tiss.<НазваниеПроекта>.Backend.slnx`**.  
   Пример: `Tiss.Orders.Payments.Backend.slnx` → `<НазваниеПроекта>` = `Orders.Payments`.
3. Если solution не соответствует формату **`Tiss.<НазваниеПроекта>.Backend.slnx`** — спросить у пользователя **название проекта**.
4. **Название сервиса**: обязательно спросить у пользователя. Название сервиса — латиница, слова/цифры; без префикса `Tiss`, без названия проекта и без имени слоя.

# Нормализация имён
- **Название проекта**:
  - если оно взято из solution — использовать значение между `Tiss.` и `.Backend`;
  - если его пришлось спросить у пользователя — нормализовать в **PascalCase**;
  - для составного названия через точку каждый сегмент нормализовать отдельно, точки сохранить: `orders.payments` → `Orders.Payments`.
- **Название сервиса** всегда нормализовать в **PascalCase** перед использованием в путях, имени solution folder и именах `.csproj`.
- Правила PascalCase:
  - каждое слово начинается с большой буквы, остальные буквы маленькие;
  - пробелы, дефисы и подчёркивания внутри одного сегмента убираются: `invoice processing` → `InvoiceProcessing`;
  - если введены точки, каждый сегмент нормализуется отдельно, точки сохраняются: `payments.api` → `Payments.Api`.
- В командах и путях использовать только нормализованные значения **`<НазваниеПроекта>`** и **`<НазваниеСервиса>`**.

# Именование
Имена проектов формируются строго по шаблону:

```text
Tiss.<НазваниеПроекта>.<НазваниеСервиса>.<НазваниеСлоя>
```

Где:
- `<НазваниеПроекта>` — берётся из имени solution или из ответа пользователя.
- `<НазваниеСервиса>` — берётся из ответа пользователя.
- `<НазваниеСлоя>` — один из: `Api`, `Application`, `Domain`, `Infrastructure`, `Tests`.

Пример:
- solution: `Tiss.Billing.Backend.slnx`
- сервис: `invoices processing` → нормализованное имя `InvoicesProcessing`
- папка сервиса: `src/InvoicesProcessing/`
- проекты:
  - `Tiss.Billing.InvoicesProcessing.Api`
  - `Tiss.Billing.InvoicesProcessing.Application`
  - `Tiss.Billing.InvoicesProcessing.Domain`
  - `Tiss.Billing.InvoicesProcessing.Infrastructure`
  - `Tiss.Billing.InvoicesProcessing.Tests`

# Расположение и группировка
- Все сервисы создаются **в папке `src/` текущего solution**.
- Каждый сервис создаётся **в своей подпапке**: **`src/<НазваниеСервиса>/`**.
- Все проекты слоёв конкретного сервиса располагаются внутри этой подпапки:

  ```text
  src/<НазваниеСервиса>/
    Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Api/
    Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Application/
    Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Domain/
    Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Infrastructure/
    Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Tests/
  ```

- Чтобы VS Code / Solution Explorer группировал проекты по сервисам, при добавлении проектов в `.slnx` использовать **solution folder** с именем сервиса:

  ```bash
  --solution-folder <НазваниеСервиса>
  ```

- Не полагаться только на физические папки: для группировки в UI нужен именно `dotnet sln ... add ... --solution-folder <НазваниеСервиса>`.

# Порядок работы
1. **Проверить SDK и solution**:
   - использовать **.NET 10** (`net10.0`);
   - работать с **`.slnx`**, не создавать `.sln`;
   - определить `<НазваниеПроекта>` из solution или спросить у пользователя и нормализовать в PascalCase.

2. **Запросить название сервиса**:
   - если название уже явно дано пользователем — использовать его;
   - иначе спросить: «Как назвать сервис?»;
   - нормализовать ответ в PascalCase и дальше использовать только нормализованное **`<НазваниеСервиса>`**.

3. **Создать проекты слоёв**:

   ```bash
   dotnet new webapi -n Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Api -o src/<НазваниеСервиса>/Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Api -f net10.0 --no-openapi
   dotnet new classlib -n Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Application -o src/<НазваниеСервиса>/Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Application -f net10.0
   dotnet new classlib -n Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Domain -o src/<НазваниеСервиса>/Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Domain -f net10.0
   dotnet new classlib -n Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Infrastructure -o src/<НазваниеСервиса>/Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Infrastructure -f net10.0
   dotnet new xunit -n Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Tests -o src/<НазваниеСервиса>/Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Tests -f net10.0
   ```

   Для проекта **Tests** не писать тестовые сценарии без прямого запроса. Правила тестового проекта и тестового кода брать из отдельного skill для тестов; в этом репозитории для unit-тестов применять **`.ai/skills/dotnet/dotnet_unit_tests_xunit_moq.md`**.

4. **Добавить проекты в solution и сгруппировать по сервису**:

   ```bash
   dotnet sln <SolutionFile>.slnx add src/<НазваниеСервиса>/Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Api/Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Api.csproj --solution-folder <НазваниеСервиса>
   dotnet sln <SolutionFile>.slnx add src/<НазваниеСервиса>/Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Application/Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Application.csproj --solution-folder <НазваниеСервиса>
   dotnet sln <SolutionFile>.slnx add src/<НазваниеСервиса>/Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Domain/Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Domain.csproj --solution-folder <НазваниеСервиса>
   dotnet sln <SolutionFile>.slnx add src/<НазваниеСервиса>/Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Infrastructure/Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Infrastructure.csproj --solution-folder <НазваниеСервиса>

   dotnet add src/<НазваниеСервиса>/Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Tests/Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Tests.csproj reference src/<НазваниеСервиса>/Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Domain/Tiss.<НазваниеПроекта>.<НазваниеСервиса>.Domain.csproj
   ```

6. **Подключить обязательные паттерны и пакеты**:
   - **Application**: CQRS, MediatR, FluentValidation, Result pattern, pipeline validation; фичи группируются **по сущностям**, затем по конкретной фиче.
   - **Domain**: сущности, value objects, events, enums; один объект = один файл.
   - **Infrastructure**: реализации портов Application, внешние клиенты, БД и всё, что относится к БД.
   - **Api**: Serilog как логгер хоста, HealthCheck, DI-регистрация слоёв, контроллеры без бизнес-логики.
   - **Tests**: только каркас проекта; правила тестов — отдельный skill.

7. **Контроллеры**:
   - не содержат бизнес-логики;
   - принимают HTTP-запрос;
   - вызывают application use case через MediatR;
   - маппят Result в HTTP-ответ.

8. **CRUD endpoint'ы**:
   - при создании микросервиса по Clean Architecture endpoint'ы создаются по CRUD-модели для основной сущности/ресурса;
   - базовый набор endpoint'ов: `Create`, `GetById`, `List`, `Update`, `Delete`;
   - HTTP-контракт: `POST /<resource>`, `GET /<resource>/{id}`, `GET /<resource>`, `PUT /<resource>/{id}`, `DELETE /<resource>/{id}`;
   - каждый endpoint вызывает отдельный MediatR command/query;
   - Application-фичи для CRUD группируются по схеме `Features/<Entity>/<CrudOperation>/`;
   - не создавать нестандартные action endpoint'ы (`Approve`, `Cancel`, `Process`, `Sync`) без прямого запроса пользователя.

9. **Структура Domain**:

   ```text
   Entities/
   Events/
   Enums/
   ValueObjects/
   ```

10. **Структура Application**:
- Фичи обязательно группируются **по сущностям**: сначала папка сущности, внутри неё папки конкретных фич.
- Не создавать фичи плоско в `Features/` без папки сущности.

   ```text
   Features/
     <Entity>/
       <Feature>/
         <CommandOrQuery>.cs
         <Handler>.cs
         <Validator>.cs
   Common/
     Behaviors/
     Results/
   ```

11. **Проверка**:

   ```bash
   dotnet build <SolutionFile>.slnx
   ```

# Формат вывода
1) **План**: solution, исходные и нормализованные названия проекта/сервиса, имена слоёв, ссылки между проектами.
2) **Результат (Deliverable)**: созданные проекты в `src/<НазваниеСервиса>/`, добавленные ссылки, solution folder для группировки, подключённые пакеты/регистрации.
3) **Самопроверка**: чеклист ниже.

# Планка качества (самопроверка)
- [ ] Для полноценного создания сервиса senior-subagent делегировал в `.ai/subagents/dotnet/clean_architecture_service_builder.md`, а этот файл прочитан как skill-contract.
- [ ] Название сервиса запрошено или явно задано пользователем.
- [ ] Название проекта взято из solution **`Tiss.<НазваниеПроекта>.Backend.slnx`** или уточнено у пользователя.
- [ ] Название проекта и название сервиса нормализованы в **PascalCase**; для составных имён через точку каждый сегмент нормализован отдельно.
- [ ] Все проекты названы по шаблону **`Tiss.<НазваниеПроекта>.<НазваниеСервиса>.<Слой>`**.
- [ ] Все проекты сервиса физически лежат в **`src/<НазваниеСервиса>/`**.
- [ ] При добавлении в `.slnx` использован **`--solution-folder <НазваниеСервиса>`**, чтобы VS Code / Solution Explorer группировал слои по сервису.
- [ ] Все проекты используют **net10.0**.
- [ ] Контроллеры не содержат бизнес-логики и вызывают Application через MediatR.
- [ ] Endpoint'ы созданы по CRUD-набору `Create`, `GetById`, `List`, `Update`, `Delete` для основной сущности/ресурса.
- [ ] Если основная сущность/ресурс не указаны пользователем, они запрошены отдельно и не выдуманы агентом.
- [ ] Подключены CQRS, Result, MediatR, Serilog, HealthCheck и FluentValidation.
- [ ] Фичи в Application сгруппированы по схеме **`Features/<Entity>/<Feature>/`**.
- [ ] Каждый файл содержит только один объект.
- [ ] Для Tests не созданы тестовые сценарии без отдельной команды.
- [ ] `dotnet build <SolutionFile>.slnx` проходит успешно.

# Анти-паттерны
- ❌ Запускать полноценное создание сервиса как обычный skill без subagent route.
- ❌ Выбирать несколько skills/routes одновременно для одного запроса на создание сервиса.
- ❌ Создавать сервис без названия сервиса от пользователя.
- ❌ Использовать введённое название проекта или сервиса без нормализации в **PascalCase**.
- ❌ Называть проекты не по шаблону `Tiss.<НазваниеПроекта>.<НазваниеСервиса>.<Слой>`.
- ❌ Создавать проекты сервиса плоско в `src/` без подпапки `src/<НазваниеСервиса>/`.
- ❌ Добавлять проекты в `.slnx` без `--solution-folder <НазваниеСервиса>`, если нужно группировать слои по сервисам в VS Code.
- ❌ Создавать фичи плоско в `Features/` без группировки по сущностям.
- ❌ Создавать endpoint'ы не по CRUD-модели без прямого запроса пользователя.
- ❌ Выдумывать основную сущность/ресурс для CRUD endpoint'ов, если пользователь её не указал.
- ❌ Размещать бизнес-логику в контроллерах.
- ❌ Добавлять ссылку Domain → Infrastructure или Domain → Application.
- ❌ Создавать тестовые сценарии в Tests без прямого запроса.
- ❌ Создавать `.sln` вместо работы с `.slnx`.
