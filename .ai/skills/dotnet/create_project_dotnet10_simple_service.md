# Назначение
Создать **простой .NET 10 сервис** с минимальной структурой, когда пользователю нужен быстрый backend, Minimal API, Worker Service, webhook, CRUD, уведомления или фоновый процесс без Clean Architecture.

# Роль skill-contract
Этот файл — **skill-contract** для subagent route:

```text
.ai/subagents/dotnet/simple_service_builder.md
```

Subagent отвечает за исполнение, а этот contract задаёт правила структуры, входные данные, ограничения и quality gates.

# Когда применять
- Пользователь просит простой `.NET` / `C#` сервис, API, worker или backend.
- В запросе есть сигналы: `CRUD`, `простой`, `minimal api`, `worker`, `прототип`, `небольшой`, `быстро`, `webhook`, `уведомления`, `фоновый`.
- Нет явных требований к DDD, CQRS, Clean Architecture, bounded context, enterprise-структуре или нескольким командам.

# Когда не применять
- Если запрос короткий и неясный — вернуть управление senior-subagent для делегирования в `.ai/subagents/dotnet/dotnet_project_clarifier.md`.
- Если пользователь явно просит DDD, CQRS, Clean Architecture, MediatR, bounded context, enterprise или масштаб на несколько команд — вернуть управление senior-subagent для делегирования в `.ai/subagents/dotnet/clean_architecture_service_builder.md`.
- Если одновременно есть сигналы простого сервиса и Clean Architecture — вернуть управление senior-subagent для уточнения route.

# Preflight blockers
Если в запросе пользователя нет названия сервиса:

1. Сразу спросить:

   ```text
   Как назвать сервис? Название укажите латиницей, без префикса Tiss, без названия проекта и без типа проекта.
   ```

2. Сразу остановиться после вопроса.
3. Не искать `.slnx`, не выполнять shell-команды, не строить план создания и не создавать файлы до ответа пользователя.

Если неясно, нужен **Minimal API** или **Worker Service**, спросить:

```text
Какой тип простого сервиса создать: Minimal API или Worker Service?
```

# Входные данные
1. **Тип сервиса**: `Minimal API` или `Worker Service`.
2. **Solution**: найти активный `.slnx`. Если файлов несколько — спросить, какой использовать.
3. **Название проекта**: взять из имени solution по формату `Tiss.<НазваниеПроекта>.Backend.slnx`.
4. Если solution не соответствует формату `Tiss.<НазваниеПроекта>.Backend.slnx` — спросить у пользователя название проекта.
5. **Название сервиса**: обязательно получить от пользователя. Название — латиница, слова/цифры; без префикса `Tiss`, без названия проекта и без типа проекта.

# Нормализация имён
- Название проекта:
  - если оно взято из solution — использовать значение между `Tiss.` и `.Backend`;
  - если его пришлось спросить — нормализовать в **PascalCase**;
  - для составного названия через точку каждый сегмент нормализовать отдельно, точки сохранить.
- Название сервиса нормализовать в **PascalCase** перед использованием в путях, имени solution folder и `.csproj`.
- В командах и путях использовать только нормализованные значения.

# Именование
Имя проекта формируется строго по шаблону:

```text
Tiss.<НазваниеПроекта>.<НазваниеСервиса>
```

Пример:
- solution: `Tiss.Billing.Backend.slnx`
- сервис: `notifications worker` → `NotificationsWorker`
- проект: `Tiss.Billing.NotificationsWorker`
- папка: `src/NotificationsWorker/`

# Расположение
Сервис создаётся в отдельной папке:

```text
src/<НазваниеСервиса>/
  Tiss.<НазваниеПроекта>.<НазваниеСервиса>/
```

При добавлении в `.slnx` использовать solution folder:

```bash
--solution-folder <НазваниеСервиса>
```

# Этапы исполнения subagent
1. **Solution Inspector**:
   - найти активный `.slnx`;
   - определить `<НазваниеПроекта>` из имени solution или подготовить вопрос пользователю;
   - проверить доступность .NET SDK 10.x;
   - посмотреть существующие сервисы, чтобы не конфликтовать с именами.

2. **Scaffold Builder**:
   - для Minimal API создать `webapi` проект с `net10.0`;
   - для Worker Service создать `worker` проект с `net10.0`;
   - добавить проект в `.slnx` с `--solution-folder <НазваниеСервиса>`.

3. **Composition**:
   - оставить простую структуру одного проекта;
   - добавить только папки, нужные выбранному типу сервиса;
   - не создавать `Domain`, `Application`, `Infrastructure`, `Tests` без прямой команды;
   - не подключать MediatR, CQRS, FluentValidation или Result pattern без прямого требования.

4. **Build Validator**:
   - выполнить `dotnet build <SolutionFile>.slnx`;
   - исправить очевидные ошибки компиляции, возникшие из-за каркаса;
   - если ошибка требует продуктового/архитектурного решения, остановиться и спросить пользователя.

# Команды
Для Minimal API:

```bash
dotnet new webapi -n Tiss.<НазваниеПроекта>.<НазваниеСервиса> -o src/<НазваниеСервиса>/Tiss.<НазваниеПроекта>.<НазваниеСервиса> -f net10.0 --no-openapi
dotnet sln <SolutionFile>.slnx add src/<НазваниеСервиса>/Tiss.<НазваниеПроекта>.<НазваниеСервиса>/Tiss.<НазваниеПроекта>.<НазваниеСервиса>.csproj --solution-folder <НазваниеСервиса>
```

Для Worker Service:

```bash
dotnet new worker -n Tiss.<НазваниеПроекта>.<НазваниеСервиса> -o src/<НазваниеСервиса>/Tiss.<НазваниеПроекта>.<НазваниеСервиса> -f net10.0
dotnet sln <SolutionFile>.slnx add src/<НазваниеСервиса>/Tiss.<НазваниеПроекта>.<НазваниеСервиса>/Tiss.<НазваниеПроекта>.<НазваниеСервиса>.csproj --solution-folder <НазваниеСервиса>
```

# Формат вывода
1) **Plan**: выбранный route, тип сервиса, solution, исходные и нормализованные названия.
2) **Deliverable**: созданный проект, путь, добавление в `.slnx`, выбранный шаблон.
3) **Self-check**: чеклист ниже.

# Анти-паттерны
- Создавать Clean Architecture слои для простого сервиса.
- Подключать MediatR, CQRS, FluentValidation, Result pattern или DDD-структуру без прямого требования.
- Создавать сервис без названия сервиса от пользователя.
- Создавать `.sln` вместо работы с `.slnx`.
- Создавать тестовые сценарии без прямого запроса.
