# Назначение
Добавить или проверить инфраструктуру конкретной **БД** в слое **Infrastructure** существующего .NET Clean Architecture сервиса.

# Когда применять
- Пользователь просит подключить БД к существующему сервису.
- Нужно добавить `DbContext`, модели БД, конфигурации, миграции или реализации портов доступа к данным.
- Нужно проверить, что БД не размазана по Application/Domain/Api.

# Входные данные
1. **Сервис**: имя или путь к существующему сервису. Если сервисов несколько — спросить.
2. **Тип БД**: например `Postgres`, `SqlServer`, `MongoDb`. Если не указан — спросить.
3. **Назначение БД**: какие данные хранит и какие Application-порты нужно реализовать.
4. **ORM/драйвер**: использовать существующий стиль проекта. Если стиля нет — предложить минимальный вариант и согласовать.

# Расположение
Всё, что относится к конкретной БД, размещать внутри Infrastructure в отдельной папке:

```text
Infrastructure/
  Persistence/
    <DatabaseType>/
      Models/
      Configurations/
      Migrations/
      Repositories/
      <Service>DbContext.cs
      DependencyInjection.cs
      <DatabaseType>Settings.cs
```

Если в проекте уже принят другой корневой каталог для persistence, использовать существующий стиль, но сохранить правило: **для каждого вида БД своя папка**.

# Порядок работы
1. Найти проекты `Application`, `Domain` и `Infrastructure` выбранного сервиса.
2. Проверить существующие порты в Application и доменные модели в Domain.
3. Создать или дополнить папку конкретной БД в Infrastructure.
4. Разместить модели для работы с БД в `Models/`; не смешивать их с Domain entities.
5. Разместить конфигурации ORM/драйвера в `Configurations/`.
6. Разместить миграции в `Migrations/`, если выбранный стек их использует.
7. Реализации Application-портов разместить в `Repositories/` или локально принятой папке для data access.
8. Добавить DI-регистрацию Infrastructure для выбранной БД.
9. Не добавлять бизнес-логику в репозитории. При спорной логике использовать `.ai/skills/engineering/repository_layer_audit.md`.
10. Выполнить сборку solution или проекта после изменений.

# Формат вывода
1) **План**: сервис, тип БД, папка Infrastructure, модели/контекст/конфигурации, Application-порты.
2) **Результат (Deliverable)**: созданные/изменённые файлы БД, DI-регистрация, пакеты, настройки.
3) **Самопроверка**: чеклист ниже.

# Планка качества (самопроверка)
- [ ] Всё, что относится к БД, находится в Infrastructure.
- [ ] Для конкретного вида БД создана или использована отдельная папка.
- [ ] Модели БД отделены от Domain entities.
- [ ] Domain не зависит от Infrastructure.
- [ ] Application зависит только от портов/интерфейсов, а не от конкретной БД.
- [ ] Репозитории не содержат бизнес-логики.
- [ ] Один файл содержит только один объект.
- [ ] Сборка проекта или solution проверена.

# Анти-паттерны
- ❌ Размещать `DbContext`, database models или migrations вне Infrastructure.
- ❌ Складывать разные виды БД в одну общую папку без разделения.
- ❌ Использовать Domain entities как persistence models без явного проектного решения.
- ❌ Добавлять ссылку Domain → Infrastructure.
- ❌ Добавлять бизнес-правила в repository/DbContext.
