# Назначение
Быстро проверить локальные изменения перед push в ветку по общему стандарту [`docs/review/CODE_REVIEW.md`](../../../docs/review/CODE_REVIEW.md).

# Когда использовать
- Пользователь просит проверить текущие изменения перед push.
- Нужно понять, можно ли безопасно отправлять локальный diff в ветку.
- До создания MR / PR.

# Входные данные
- Текущий `git diff` или список изменённых файлов.
- Краткий контекст задачи, если он есть.

# Процедура
1) Прочитать общий стандарт [`docs/review/CODE_REVIEW.md`](../../../docs/review/CODE_REVIEW.md).
2) Определить границу локальных изменений.
3) Проверить явные регрессии, лишние файлы, нарушение слоёв и бизнес-логику в репозиториях к БД.
4) Проверить, не попали ли в diff секреты, временные файлы, отладочный код или unrelated refactoring.
5) Сформировать короткий список блокеров перед push и команд проверки.

# Формат вывода
1) **Можно push:** `да` | `нет`
2) **Блокеры перед push** (до 5): файл/символ — проблема — что исправить
3) **Локальные правки:** что поправить до push
4) **Проверки:** какие команды или сценарии прогнать
5) **Риски для MR:** что отдельно проверить после создания MR

# Планка качества (self-check)
- [ ] Ответ короткий и сфокусирован на готовности к push.
- [ ] Блокеры привязаны к конкретным файлам или рискам.
- [ ] Проверена бизнес-логика в репозиториях к БД, если затронут persistence.
- [ ] Не требуется полноценное MR-review без MR-контекста.

# Антипаттерны
- ❌ Делать глубокое MR-review без MR / PR контекста.
- ❌ Требовать unrelated refactoring перед push.
- ❌ Переписывать код вместо списка конкретных замечаний, если правки не просили.
