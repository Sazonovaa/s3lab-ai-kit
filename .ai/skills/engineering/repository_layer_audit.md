# Purpose
Проверить, что классы `*Repository*` содержат **только доступ к данным** (запросы, маппинг сущностей). Если найдена **бизнес-логика** — обязательная секция **«Рефакторинг»** с конкретным планом.

# When to use
- Любая работа с файлом/классом, совпадающим с `*Repository*`.
- Ревью PR, затрагивающего persistence.

# Procedure
1) Прочитать класс целиком: ветвления по **доменным смыслам**, композиция юз-кейсов, валидация бизнес-правил внутри репозитория.
2) Если чисто data mapping / CRUD / спецификации запросов — зафиксировать **OK** с коротким обоснованием.
3) Если нарушение: перечислить **конкретные строки/методы** и тип нарушения (бизнес-ветка, оркестрация, дублирование use case).
4) Секция **Рефакторинг**: куда вынести (domain service, application handler, specification, MediatR handler — по принятой архитектуре), **пример сигнатур**, минимальный **план миграции** (шаги PR).
5) Не переписывать код без запроса — только аудит и план.

# Output format
1) **Verdict:** `clean` | `needs_refactor`
2) **Findings** (список нарушений с путями)
3) **Рефакторинг** (обязательно при `needs_refactor`):
   - Целевые типы/слои
   - Пример интерфейсов/методов после выноса
   - Порядок шагов (1..n)
4) **Tests:** что покрыть моками после выноса

# Quality bar (self-check)
- [ ] Нет общих слов без привязки к коду.
- [ ] План миграции выполним небольшими PR.
- [ ] Учтены существующие bounded context / слои проекта, если видны из контекста.

# Anti-patterns
- ❌ «Переписать всё на DDD» без конкретных шагов.
- ❌ Требовать рефакторинг, когда класс только строит `IQueryable` без доменных ветвей.
