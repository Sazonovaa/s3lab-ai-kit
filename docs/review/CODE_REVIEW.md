# Стандарт code review

## Назначение

Используйте этот стандарт для ручного и AI-assisted code review в этом репозитории.

## Приоритеты ревью

1. Корректность, регрессии и пограничные сценарии.
2. Контракты публичного API и обратная совместимость.
3. Безопасность, авторизация и риски утечки данных.
4. Границы Clean Architecture.
5. Persistence, миграции и владение базой данных.
6. Отсутствие бизнес-логики в репозиториях к БД.
7. Тесты, логирование и наблюдаемость.
8. Именование, читаемость и поддерживаемость.
9. Соответствие файловым правилам: CRLF для текстовых файлов перед коммитом.

## Правила архитектуры

- Код Domain не должен зависеть от Infrastructure, Web, database clients, HTTP clients или framework-specific деталей.
- Код Application должен отделять orchestration, validation и use-case logic от transport и persistence деталей.
- Infrastructure владеет настройкой БД, database models, repositories, external integrations, settings и API clients.
- Код, связанный с БД, должен быть сгруппирован по типу БД внутри Infrastructure.
- Репозитории к БД должны содержать только доступ к данным: CRUD, построение запросов, mapping и persistence-specific операции.
- В репозиториях к БД не должно быть бизнес-логики: доменных ветвлений, orchestration use case, validation бизнес-правил или принятия бизнес-решений.
- Aggregate roots должны находиться в `Entities/`.
- Domain events должны находиться в `Events/`.
- Enums должны находиться в `Enums/`.
- Value objects должны находиться в `ValueObjects/`.
- В одном файле описывайте только один объект.

## Правила стиля и реализации

- Между свойствами DTO, request и response оставляйте пустые строки.
- `using` сортируйте в алфавитном порядке.
- Свойства, зависимости, параметры конструктора и поля ответа сортируйте в алфавитном порядке, если это не ухудшает читаемость и не ломает существующий стиль файла.
- Для коллекций входных данных с `init` используйте `IReadOnlyList<T>` вместо `ICollection<T>`, если коллекция не должна изменяться через `Add`/`Remove`.
- Свойства типа `IReadOnlyList<T>` располагайте ниже простых scalar-свойств.
- Для проверок коллекций используйте `Count > 0`, если тип коллекции уже предоставляет `Count`.
- Проверки входных данных размещайте в validator-е, а не в handler-е, если это validation-only логика.
- Простые условные присваивания пишите тернарным оператором, если это не ухудшает читаемость.
- В простых LINQ-выражениях без вложенных лямбд используйте имя параметра `x`. Если есть вложенные лямбда-выражения, используйте осмысленные имена по типу или роли объекта, чтобы не было конфликта и ухудшения читаемости.
- Не используйте AutoMapper для создания или изменения доменных entity в сценариях, где важна явная бизнес-логика. Entity заполняйте явно.
- Не передавайте строковые include-пути напрямую из application-слоя, например `nameof(User.UserRoles) + "." + nameof(UserRole.Role)`. Используйте специализированный метод репозитория, загрузку внутри Infrastructure или убирайте лишнюю загрузку.
- Повторяющуюся генерацию значений выносите в общий helper/service, например генерацию password или refresh token.
- Не добавляйте сервисы, которые не участвуют в сценарии. Неиспользуемые классы, интерфейсы и DI-регистрации удаляйте.
- Для новых собственных методов проекта не используйте суффикс `Async`, если в проекте принят стиль без `Async`. Внешние интерфейсы и framework-контракты не переименовывайте.
- Не дублируйте уже существующую логику проекта. Перед добавлением helper/service проверяйте, есть ли аналогичный код в существующих сервисах.
- `CancellationToken` пробрасывайте из controller endpoints в MediatR/request handlers и далее в repository/service вызовы, где это поддерживается.

## Правила тестов

- Для unit-тестов в этом репозитории используйте `xUnit + Moq`.
- Не добавляйте NUnit.
- Unit-тесты не должны зависеть от реальной БД.
- Предпочитайте сфокусированные тесты вокруг изменённого поведения и публичных контрактов.
- Не добавляйте тестовые сценарии, если задача явно этого не требует.

## Правила файлов

- Все текстовые файлы перед коммитом должны использовать CRLF line endings.
- Проверка выполняется через `scripts/validations/validate-crlf.ps1`.
- Git hooks устанавливаются через `scripts/hooks/install-git-hooks.cmd`.

## Формат ревью

Сначала возвращайте замечания, отсортированные по важности.

1. **Вердикт:** `approve`, `approve_with_nits` или `request_changes`.
2. **Блокеры:** файл/символ, проблема, почему это важно, как проверить исправление.
3. **Nits:** небольшие замечания по поддерживаемости или именованию.
4. **Тесты:** что добавить или запустить.
5. **Вопросы:** только если контракт или намерение неясны.

## Ограничения ревью

- Не запрашивайте несвязанный с задачей рефакторинг.
- Не переписывайте код, если об этом явно не попросили.
- Предпочитайте конкретные проектные замечания вместо общих советов.
- Считайте замечания только по форматированию nits, если за ними не скрывается реальная проблема.
- Держите ревью кратким и применимым.
